# 项目介绍 · 换电运营平台多板块数据看板

## 一、一句话介绍

面向两轮车换电 / 租车业务的**运营数据看板系统**：把我原本需要跨多张业务表手工统计的运营数据，做成 12 个板块、60+ 个接口的可视化看板，全链路只读、多角色权限、并在业务库中断时仍能回放最近一次数据继续值班。

---

## 二、简历写法（可直接用）

**项目：换电运营平台数据看板（个人独立设计 + 开发）**

- 独立完成面向两轮车换电 / 租车业务的运营看板：Flask + AnalyticDB(MySQL 协议, 只读) + 原生 JS/ECharts，落地 12 个业务板块、60+ 个 REST 接口，覆盖运营、用户、销售、网点、设备资产、财务、运维、客服 8 类视角。
- 设计并实现**断库容灾三级兜底机制**（服务端 SQLite 缓存回放 → 连接熔断 → 前端 localStorage 兜底）：SQL 归一化取 SHA1 生成稳定缓存 key，查询失败自动回放最近一次成功结果并标记 `cached`；断库场景下 64/64 接口回放验证通过，值班看板不再白屏。
- 建立**只读访问层 + 连接熔断**约束，所有查询强制 SELECT-only 校验，生产库零写入、零慢查询放大；配套角色权限模型（admin / 客户经理 / 只读）与按客户范围的数据隔离。
- 全站前端资源本地化，适配无外网的内网值班与大屏环境；凭据仅内存读取，不落日志、不回显前端。

## 三、项目背景与要解决的问题

业务侧的真实痛点：

1. **数据分散**：换电订单、电池、换电柜、网点、用户、销售、押金、优惠券、工单分散在多张业务表，运营每天要人工拉数、拼表。
2. **角色视角不同**：运营看城市与网点、客户经理看自己名下客户、客服要实时查单个用户、管理层看大屏与趋势 —— 不能只做一个报表页。
3. **不能碰生产库**：业务库是生产环境，不允许写入，也不能让看板把库拖慢。
4. **值班不能白屏**：业务库抖动或网络中断时，值班人员仍需要能看到最近一次数据。

对应设计目标：**只读、多角色、可降级、内网可部署**。

## 五、技术方案要点

- **分层架构**：`api/routes.py`（接口） → `core/*`（业务聚合，按主题拆模块） → `core/db.py`（只读访问 + 熔断） → `core/cache.py`（缓存 key 与落盘）；`auth/` 独立内置用户库，与业务库凭据隔离。
- **只读约束**：`query()` 强制校验语句以 `select` / `with` 开头，否则抛错；数据库账号使用只读账号；连接 / 读超时显式设置。
- **告警口径可配置**：电池饿死判定（电压阈值 + 0% 电量）、断充、烟感、水浸、仓位等告警规则与优先级写在 `config/config.yaml`，业务方调整阈值无需改代码。
- **权限模型**：权限点按板块划分（`overview:view`、`user:view`、`sales:view` …），支持自定义角色；客户经理按 `oem_ids` 限定可见数据范围。

## 六、三个可深挖的技术难点

### 难点 1：断库后看板必须"有数可看"（容灾设计）

**问题**：业务库抖动时，接口全部超时 → 前端白屏或满屏报错，值班人员无法判断是"没数据"还是"系统挂了"。

**方案（三级兜底）**：

1. 服务端：查询成功即把结果按稳定 key 落盘 SQLite（上限 3000 条，淘汰最旧）；查询失败回放最近一次成功结果，并返回 `cached: true` + `cached_at`。
2. 连接层：建连失败后 60s 熔断，避免断库期间每个请求都排队等超时。
3. 前端：请求封装在网络错误 / 非 JSON / 业务码异常三种情况下回放 localStorage 最后成功结果，并显示降级横幅。

**关键设计取舍 —— 稳定缓存 key**：时间范围参数里带毫秒时间戳，如果直接用"SQL + 参数"做 key，同一业务查询每次都会生成新 key，缓存等于失效。做法是在 `core/cache.py` 里对 SQL 做**归一化**（毫秒时间戳字面量替换为固定占位符）后再取 SHA1，保证同一业务查询跨时刻命中同一条缓存。

**结果**：64 个看板接口完成缓存预热并做断库演练，64/64 回放成功；断库期间看板正常展示历史数据并明确标注"缓存中"。

### 难点 2：在生产库上做只读看板，如何不"拖库"

- 查询统一收敛到一个访问层，禁止任何写语句；
- 显式设置连接超时（5s）与读超时（30s），慢查询不会挂住整个看板；
- 连接失败熔断，断库期间不反复重试打满连接；
- 看板侧统计尽量在 SQL 内聚合（按城市 / 网点 / 日期分组），避免把明细拉回应用层再计算。

### 难点 3：多板块 × 多角色的权限与数据隔离

- 权限点按板块与动作定义，角色可自定义；登录装饰器统一拦截，接口层不重复写权限判断；
- 客户经理角色按 `oem_ids` 做数据范围过滤，同一接口对不同角色返回不同范围的数据，避免"看得见不该看的数据"；
- 内置用户库为独立 SQLite，与业务库凭据完全隔离，密码哈希存储。

## 七、业务价值

- 运营、客服、客户经理从"人工拉表统计"转为"看板自助取数"，日常数据查看不再依赖开发临时导数据；
- 值班大屏在没有外网、业务库抖动的情况下仍可正常显示（降级标注明确），减少"系统是不是挂了"的误判与排查；
- 告警口径（电池饿死 / 断充 / 烟感 / 水浸 / 仓位）配置化，业务侧可自行调整阈值。

## 八、面试常见追问与答题要点

| 追问 | 回答要点 |
|------|----------|
| 为什么不用 BI 工具（如 Superset / Metabase）？ | 需要跨库聚合 + 自定义告警口径 + 断库容灾 + 内网零依赖；BI 工具在降级能力与业务口径定制上不满足，且引入额外运维成本。 |
| 缓存为什么不直接用 Redis？ | 部署环境为单机内网值班服务，SQLite 零运维、随服务落盘即可；缓存语义是"最近一次成功结果"，按 key upsert + 上限淘汰已足够。若要多实例部署，再抽换成 Redis。 |
| 断库时看到的是旧数据，会不会误导决策？ | 接口显式返回 `cached` 与 `cached_at`，前端固定显示降级横幅与缓存时间，用户能明确知道数据时点。 |
| 接口 60+ 个，如何保证一致性与可维护性？ | 统一访问层 + 统一响应结构 + 业务聚合按主题拆模块；筛选选项走统一字典接口，前端不硬编码枚举。 |
| 数据量大了怎么办？ | 统计在 SQL 内聚合、限定时间窗与维度；必要时把高频大盘指标做定时预聚合落地，看板只读预聚合结果。 |
| 安全性怎么保证？ | 只读账号 + SELECT-only 校验 + 凭据仅内存读取不回显不落日志 + 角色权限与数据范围隔离 + 内网白名单。 |
